# Сквозной (e2e) стенд: стандартный клиент RustDesk 1.5.0 как устройство, работающее только через WebSocket

Одноразовый стенд в Docker. Неизменённый Linux-клиент RustDesk 1.5.0 работает
с `hbbs`/`hbbr` за nginx с TLS, а межсетевой экран устройства пропускает только
`tcp/443` к прокси. Образ `hbbs` задаётся параметром (`HBBS_IMAGE`). Один и тот
же набор тестов запускается на стандартном `hbbs` из upstream (базовый прогон,
в котором ошибка должна проявиться) и на сборке с патчем.

Все объекты называются `patina-e2e-*` и удаляются по имени (`scripts/down.sh`).
Ничего не очищается командами prune, и ничего не устанавливается на хост.
Скриптам нужны только `docker` (с compose v2), `bash`, `openssl` и `git`.

## Топология

```text
              wan 10.231.1.0/24                     ctl 10.231.2.0/24
 ws-device .21 ──┐ (iptables: only tcp→.10:443)    ┌── ws-controller .21 (only tcp→.10:443)
 udp-device .22 ─┤                                 ├── udp-controller .22
 nat-router .30 ─┤  nginx .10  (TLS, rd.e2e.test)  │
   │ MASQUERADE  ├─ edge  .11  ← hbbs + hbbr share ┤
   │             │      │      this netns           │
   │             │  proxy 10.231.4.0/24: nginx .10 ─ edge .11 only
   │             │  (nginx → hbbs:21118 / hbbr:21119; TRUSTED_PROXY_CIDRS)
 lan 10.231.3.0/24 (default route via nat-router)
   nat-device-a .21, nat-device-b .22  (WS-only, default route via router)
```

* **edge** владеет IP-адресом сервера. `hbbs` и `hbbr` работают в его сетевом
  пространстве имён (netns), поэтому один адрес обслуживает порты 21115–21119,
  как на рабочем сервере, а `hbbs` можно перезапустить, не затрагивая `hbbr`.
* nginx обращается к `hbbs` и `hbbr` только через сеть `proxy` (10.231.4.0/24,
  только nginx и edge), поэтому `hbbs` видит каждое соединение через прокси
  как пришедшее с 10.231.4.10. Так повторяется подключение обратного прокси к
  `rustdesk-net` на рабочем сервере. Прямое подключение к edge:21118 из wan или
  ctl приходит не от доверенного прокси.
* WebSocket-клиенты разрешают `rd.e2e.test` в адрес nginx: `/ws/id` уходит на
  hbbs:21118, `/ws/relay` — на hbbr:21119. На `/api/` и все остальные адреса
  возвращается 404. Клиенты в режиме UDP разрешают то же имя напрямую в адрес
  edge — так рабочий сервер выглядит для обычного клиента.
* Для TLS используется одноразовый локальный центр сертификации (CA). Клиент
  доверяет ему через системное хранилище (`update-ca-certificates`), а
  `allow-insecure-tls-fallback` остаётся **выключенным**.
* Настройки клиента взяты из технического задания: `custom-rendezvous-server`
  и `relay-server` равны `rd.e2e.test`, `key` — открытому ключу `hbbs`,
  `api-server=https://rd.e2e.test` и `allow-websocket=Y`. Для доступа без
  присмотра используется постоянный пароль.
* `hbbs` запускается как `-r rd.e2e.test -k _` с `read_only`,
  `cap_drop: [ALL]`, `no-new-privileges` и uid 1000. `hbbr` — всегда
  стандартный образ, `-k _`. Стенд задаёт `WS_REGISTER=Y` и
  `TRUSTED_PROXY_CIDRS=10.231.4.0/24` — сеть `proxy`, в которой находятся
  только nginx и edge, так же как обратный прокси подключается к `rustdesk-net` на рабочем
  сервере. Стандартный `hbbs` обе переменные игнорирует.

## Контейнер клиента

* База: `debian:bookworm-slim`, закреплённый по дайджесту. Клиент — официальный
  `rustdesk-1.5.0-<arch>.deb`, проверенный по sha256. arm64 работает нативно на
  Apple Silicon, amd64 тоже поддерживается.
* Экран: Xvfb + openbox от имени непривилегированного пользователя `rd`. Захват
  экрана и ввод идут через X11, поэтому не нужны ни uinput, ни
  привилегированный режим. `NET_ADMIN` нужен только скрипту entrypoint, чтобы
  установить правила межсетевого экрана для исходящего трафика и маршрут через
  NAT.
* На устройствах запущен `rustdesk --server` — тот процесс, который служба
  systemd запустила бы в сеансе пользователя. Главное окно открывается только
  для итоговых снимков экрана: у него своя копия `RustDesk.toml`, и оно может
  перезаписать то, что записал `--server`.
* В контейнерах нет systemd-logind, поэтому тестовая заглушка
  `/usr/local/bin/loginctl` сообщает об одном активном сеансе X11 на seat0 для
  `rd` — так выглядит рабочий стол, на котором выполнен вход. Клиент читает эти
  данные, чтобы заполнить `PeerInfo.username`. Без заглушки стандартный
  управляющий клиент отказывается передавать файлы с сообщением «No active
  console user logged on». Бинарный файл RustDesk не изменён.
* У каждого контейнера свой `/etc/machine-id`, из которого клиент получает свой
  uuid. Id сохраняется после `docker restart`, как у настоящего компьютера.
  Пересозданный контейнер — это новый компьютер, поэтому в тестах перезапуска
  контейнеры не пересоздают.
* Каждый контейнер закрашивает рабочий стол своим однотонным цветом. Если на
  снимке экрана управляющего устройства большая область окрашена в цвет
  устройства, значит, удалённый рабочий стол показывает именно это устройство.

## Использование

```bash
cd tests/e2e
scripts/build-stock.sh                       # stock hbbs/hbbr from 873230e (git archive, ~10 min)
# patched build from exact commits, no checkout (context = git archive + hbb_common at its pin):
scripts/build-image.sh <hbbs-commit> --dockerfile <packaging-commit>:Dockerfile   # -> patina-e2e-hbbs:<sha7>
docker build -t patina-e2e-client:1.5.0 client
docker build -t patina-e2e-probe:latest --build-context protos=../../libs/hbb_common/protos probe

scripts/run-matrix.sh                        # baseline: HBBS_IMAGE defaults to the stock build
HBBS_IMAGE=patina-e2e-hbbs:<sha7> scripts/run-matrix.sh all    # patched, including the 11 min idle test
scripts/down.sh                              # remove containers, networks, volumes
scripts/down.sh --images                     # ...and the patina-e2e-* images
```

Результаты сохраняются в `$E2E_STATE/out` (по умолчанию
`$TMPDIR/patina-e2e-state/out`): `results.tsv`, `run-info.txt` (дайджесты
образов), снимки экрана, журналы docker всех контейнеров и журналы клиентов
RustDesk. Можно запустить только часть тестов:
`scripts/run-matrix.sh ready desktop spoof`.

`down.sh` не удаляет кэш сборки Docker. Для этого понадобилась бы команда
prune, а этот стенд её никогда не запускает.

## Тесты и критерии их прохождения

| тест | автоматическая проверка |
|------|-----------------|
| `ready` | У устройства, работающего только через WebSocket, в `RustDesk.toml` есть `key_confirmed = true` и флаг для этого хоста. Клиент выставляет их только после `RegisterPkResponse.OK`, и строка «Готов» (Ready) в интерфейсе читает те же флаги. |
| `firewall` | Устройство не может открыть tcp/21116 на edge. Дамп правил iptables сохраняется. |
| `desktop` | Управляющее WebSocket-устройство запускает `rustdesk --connect <id> --password …`. Цвет устройства должен занимать больше `MIN_SHARE`% (по умолчанию 5) экрана управляющего устройства. |
| `filetransfer` | Устройство записывает случайный токен в `~/PATINA_E2E_MARKER.txt`. Управляющее устройство запускает `rustdesk --file-transfer <id> --password …`, затем xdotool выбирает файл на удалённой панели и нажимает Receive (фиксированная раскладка 1280x800). Копия у управляющего устройства должна содержать токен. |
| `online` / `offline` | Пробник отправляет клиентский `OnlineRequest` через `wss /ws/id`. Устройство должно быть в сети, а через 5 с после остановки — не в сети. Снимок списка узлов на управляющем устройстве сохраняется для визуальной проверки индикатора (ВРУЧНУЮ). |
| `idle` | Готовое устройство и открытый удалённый сеанс оставляются без действий на `IDLE_SECONDS` (по умолчанию 660). Тест пройден, если в журнале клиента нет нового переподключения `start tcp:`, устройство по-прежнему в сети, а сеанс по-прежнему показывает экран. |
| `restart_hbbs` / `restart_nginx` / `restart_device` | После `docker restart` в журнале клиента должно появиться новое переподключение `start tcp:`. Затем `hbbs` должен снова сообщить, что устройство в сети (`OnlineRequest`, опрос каждые 3 с, не дольше `RESTART_TIMEOUT`=150 с), с тем же ID и без нового `UUID_MISMATCH`. Записываются время восстановления и число строк `peer <id> registered` в журнале `hbbs`. Сохранённый на диске клиента `key_confirmed` переживает перезапуск, поэтому здесь он доказательством не считается. |
| `udp_to_ws` (+`_filetransfer`) | Управляющее устройство в режиме UDP открывает рабочий стол WebSocket-устройства и копирует файл-метку. |
| `ws_to_udp` (+`_filetransfer`) | Управляющее WebSocket-устройство открывает рабочий стол устройства в режиме UDP и копирует файл-метку. Это проверка на регрессию; на стандартном сервере она проходит. |
| `nat` | Два WebSocket-устройства за одним маршрутизатором с MASQUERADE оба готовы и в сети, и управляющее устройство открывает рабочий стол каждого из них. |
| `keepalive` | Пробник регистрируется через nginx и держит соединение 45 с, отвечая эхом на кадры. Нужны ответ RegisterPk OK, значение `keep_alive` в ответе, пустые бинарные кадры от сервера с промежутками короче `keep_alive` и соединение, всё ещё открытое в конце. |
| `replace` | Замена при переподключении и перехват ID, через nginx. Пробник A регистрирует id X. Пробник B регистрирует X с теми же uuid и pk, как это сделало бы переподключающееся устройство. Пробник C пытается занять X с другим uuid. Тест пройден, если A получает OK и затем сервер закрывает его соединение, B получает OK и остаётся подключённым с keepalive-кадрами, C получает `UUID_MISMATCH`, X в сети, пока его держит B, а в журнале `hbbs` есть строка `replaces`. |
| `spoof` | Пробник подключается **напрямую** к edge:21118, который не является доверенным прокси, с подделанными `X-Real-IP`/`X-Forwarded-For` и регистрирует новый id. IP-адрес, который `hbbs` сохраняет в записи узла, должен быть настоящим адресом пробника, а не подделанным. На стандартном `hbbs` WebSocket `RegisterPk` получает NOT_SUPPORT, поэтому ничего не сохраняется, и результат — SKIP. |
| `trusted_proxy` | Положительный контроль: та же регистрация через nginx (доверенный прокси) должна сохранить адрес пробника из `X-Real-IP`, а не собственный адрес nginx в сети `proxy` (10.231.4.10), который `hbbs` на самом деле видит как узел. |
| `gui_status` | Снимки главного окна каждого устройства (ВРУЧНУЮ: строка статуса должна показывать «Готов», Ready). |

## Пробник

`probe/probe.py` — простой WebSocket-клиент на классах protobuf, сгенерированных
из `rendezvous.proto` закреплённой версии `hbb_common`:

```bash
docker compose -p patina-e2e -f compose.yaml --profile probe run --rm probe \
    register ws://10.231.1.11:21118/ws/id --id test123 --header 'X-Real-IP: 1.2.3.4' --hold 60
... probe online wss://rd.e2e.test/ws/id --peers 123456789 --brief
... probe dbinfo --id test123
```

`register --hold N` также отвечает эхом на пустые keepalive-кадры сервера и
записывает время их получения — так можно измерить интервал keepalive.

## Ограничения стенда

* Управляющее устройство — стандартный клиент с графическим интерфейсом,
  которым управляют из командной строки, а для копирования файла — через
  xdotool. Удалённый ввод с клавиатуры и мыши на устройстве не проверяется.
* Индикаторы «в сети» в интерфейсе не проверяются. В этой конфигурации
  сеансы, открытые через `--connect`, не появляются в списках «Последние сеансы» (Recent) и
  «Избранное» (Favorites) стандартного интерфейса, поэтому нет карточки узла, на которую
  можно посмотреть. Проверка `OnlineRequest` на уровне протокола, которым
  интерфейс пользуется для индикатора, автоматизирована.
* Одна машина и одна виртуальная машина Docker: нет настоящих задержек WAN,
  ограничений MTU и потерь пакетов.
