# Регистрация устройств через WebSocket

Patina — небольшой форк открытого сервера RustDesk
([rustdesk/rustdesk-server](https://github.com/rustdesk/rustdesk-server),
AGPL-3.0). Главное его изменение — в `hbbs`: **стандартный клиент с
включённым параметром «Использовать WebSocket» (Use WebSocket) может быть
управляемым устройством**, даже если единственный путь к серверу —
`wss://<domain>:443` через обратный прокси. Ему не нужны ни UDP 21116, ни
прямой TCP 21115-21119. Кроме того, Patina отключает унаследованную от
исходного проекта проверку версии на `api.rustdesk.com` (см.
[«Исходящие соединения»](#исходящие-соединения)).

На стороне клиента ничего не меняется. Стандартный клиент (1.4.0 и новее,
проверено по исходному коду 1.5.0) уже поддерживает этот протокол, потому что
его поддерживает Pro-сервер. `hbbr` тоже не меняется: он уже принимает
WebSocket.

Открытый `hbbs` из исходного проекта (upstream) регистрирует устройства только
по UDP. По TCP/WebSocket он отвечает на `RegisterPk` кодом `NOT_SUPPORT` и
закрывает сокет, поэтому устройство, работающее только через WebSocket, так и
не становится «готовым» (см. rustdesk-server#657, #677 и #704).

## Как это работает

Всё описанное ниже действует только при `WS_REGISTER=Y`. При значении по
умолчанию `N` `hbbs` работает по протоколу upstream, за исключением более
строгой обработки заголовков прокси, описанной в разделе
[«Адреса за прокси»](#адреса-за-прокси).

```text
device (WS mode)             nginx :443            hbbs :21118
  | wss /ws/id  RegisterPk{id,uuid,pk} ------------------> | same checks as UDP RegisterPk
  | <---------------------- RegisterPkResponse{OK,keep_alive=36}
  |                          (connection stays open, ws_peers[id] = this conn)
  | <---------------------------------- empty binary frame  every 12 s
  | empty binary frame (echo) --------------------------> | last_reg_time = now
  ...
controller  PunchHoleRequest{id, licence_key} ---------> |
  | <------------------------------------------ PunchHole  (pushed on the device's stream)
device: new wss /ws/id   RelayResponse{socket_addr,uuid,relay,id} --> | signs IdPk with the server key
controller <-------------------------------- RelayResponse{pk = signed IdPk}
device and controller ----> hbbr (wss /ws/relay, or tcp 21117)  paired by uuid
```

* **Задача записи (writer task).** После рукопожатия WebSocket у каждого
  соединения появляется задача, которая владеет приёмником (sink). Все
  остальные отправляют данные через ограниченный канал (32 кадра,
  `try_send`; если канал полон, кадр отбрасывается), поэтому во время записи
  кадра никакая блокировка не удерживается. Как только соединение
  зарегистрировалось, задача каждые `WS_KEEPALIVE_SECS` отправляет пустой
  бинарный кадр.
* **Регистрация.** `RegisterPk` проходит через ту же функцию, что и по UDP:
  длина id, блокировка по IP, правила владения uuid/pk и `UUID_MISMATCH`,
  ограничение частоты `reg_pk`, `IP_CHANGES` и `update_pk`. При `OK`
  соединение становится маршрутом к устройству, выставляются `socket_addr` и
  `last_reg_time`, а в ответе передаётся `keep_alive` (3 × интервал keepalive,
  по умолчанию 36 с). Клиент переподключается, если за 1,5 × `keep_alive`
  ничего не получил, то есть через 54 с. Остальные результаты отправляются так
  же, как по UDP, и соединение остаётся открытым: клиент повторяет попытку
  каждые 15 с, а после `UUID_MISMATCH` создаёт себе новый id и пробует снова.
* **Один id на соединение.** После `OK` запрос `RegisterPk` с другим id
  закрывает соединение. Новое соединение, которое регистрирует тот же id (и
  проходит проверки uuid/pk), заменяет старое, и старое закрывается.
  Заменённое соединение не может вернуть себе id: пока чтение из него не
  завершится, его `RegisterPk` закрывает его, а его heartbeat и
  `RegisterPeer` ни на что не влияют.
* **Heartbeat (контрольный сигнал).** Пустой кадр от соединения, которому
  принадлежит id, обновляет `last_reg_time`. Тайм-аут чтения `hbbs` в 30 с
  остаётся, а эхо каждые 12 с не даёт ему сработать. Молчащее
  устройство отключается через 30 с.
* **`RegisterPeer`** принимается только как обновление для id, который это
  соединение зарегистрировало через `RegisterPk`. Он никогда не привязывает
  id: на непривязанный `RegisterPeer` приходит `request_pk=true`, и ничего не
  меняется. (В некоторых форках `RegisterPeer` привязывает к соединению любой
  id — это перехват ID.)
* **Маршрутизация.** `PunchHole` и `FetchLocalAddr` (их формирует
  `handle_punch_hole_request`), а также `RequestRelay` уходят в
  WebSocket-соединение устройства, если оно есть. Иначе `hbbs` использует UDP,
  как upstream. Если очередь WS-устройства полна, отправка по UDP не
  пробуется. В режиме WebSocket устройство всегда отвечает, открывая новое
  соединение `/ws/id`, которое отправляет `RelayResponse`, а затем
  подключается к `hbbr` через `wss://<domain>/ws/relay`.
* **`RequestRelay` к WS-устройству** сам называет ретранслятор и не содержит
  лицензионного ключа. Он передаётся, только если этот ретранслятор есть в
  `-r`, и отклоняется, если `-r` не задан. Иначе любой, кто знает id
  устройства, мог бы заставить устройство подключиться к выбранному им хосту и
  узнать его адрес. WS-устройству `RequestRelay` никогда не нужен: оно
  подключается к ретранслятору по `PunchHole`.
* **Статус «в сети».** В режиме WS клиент отправляет `OnlineRequest` на
  `/ws/id`, и `hbbs` отвечает там же (upstream отвечает только на 21115,
  поэтому все индикаторы показывали «не в сети»). WS-устройство считается в
  сети, если его `last_reg_time` свежий, поэтому оно в сети и для запросов
  через 21115.
* **Очистка.** Когда чтение из зарегистрированного соединения завершается,
  маршрут удаляется, если он всё ещё принадлежит этому соединению, а
  `last_reg_time` помечается устаревшим, так что устройство сразу
  показывается не в сети, а не через 30 с.
* Без изменений: `ALWAYS_USE_RELAY`, проверка лицензионного ключа в
  `PunchHoleRequest`, отключённые по UDP `PunchHoleRequest`/`PunchHoleSent`/
  `LocalAddr` (исправления upstream против атак отражения),
  `MAX_PUNCH_REQUESTS` и лимит длины id в 253 байта.

Новый код находится в `src/ws_peers.rs`; `src/rendezvous_server.rs` только
вызывает его (см. [PATCHES.ru.md](../PATCHES.ru.md)).

### Адреса за прокси

Upstream доверял `X-Real-IP` / `X-Forwarded-For` от любого, кто мог
подключиться к 21118, и заменял адрес на `IP:0`. Из-за этого клиент, который
подключался напрямую, мог выбрать себе IP (и обойти блокировку по IP), а два
управляющих устройства за одним NAT конфликтовали в `tcp_punch`, и одно из них
получало ответ, предназначенный другому.

Теперь:

* Заголовки используются, только если TCP-узел входит в `TRUSTED_PROXY_CIDRS`
  (loopback доверенный всегда). От всех остальных они игнорируются и
  записываются в журнал (не чаще одного предупреждения в минуту, со
  счётчиком).
* `X-Real-IP` должен встречаться один раз; из `X-Forwarded-For` учитывается
  только последний узел цепочки в последней строке. Если есть оба заголовка,
  они должны совпадать. Всё непригодное или противоречивое заменяется
  собственным адресом прокси (отказ в безопасную сторону, fail closed) и
  записывается в журнал. Поэтому клиент не может выбрать себе IP, добавив тот
  заголовок, которым его прокси не управляет.
* Порт берётся из `X-Real-Port` (nginx `$remote_port`), если он есть, иначе
  вычисляется из идентификатора соединения. Это только ключ для отдельного
  соединения; клиенты используют только IP.

## Настройка

Переменные окружения (читаются также из `.env` или файла `-c`, как в
upstream):

| Переменная | По умолчанию | Значение |
| --- | --- | --- |
| `WS_REGISTER` | `N` | `Y` включает регистрацию, heartbeat и статус «в сети» через WebSocket |
| `TRUSTED_PROXY_CIDRS` | (только loopback) | CIDR или IP через запятую или пробел, чьи `X-Real-IP` / `X-Forwarded-For` / `X-Real-Port` используются. **Укажите здесь сеть Docker, в которой находится прокси**, например `172.20.0.0/16`, иначе все клиенты будут выглядеть как прокси. Неправильные записи записываются в журнал и пропускаются. |
| `WS_KEEPALIVE_SECS` | `12` | Интервал пустого keepalive-кадра, ограничен диапазоном 5..20. Клиенту передаётся `keep_alive`, равный 3 × этому значению. |
| `MAX_WS_PEERS` | `10000` | Число устройств, одновременно зарегистрированных через WebSocket. Сверх него `RegisterPk` получает `SERVER_ERROR`, и соединение закрывается (уже зарегистрированный id по-прежнему может перейти на новое соединение). |
| `MAX_WS_CONN_PER_IP` | `64` | Одновременные WebSocket-соединения с одного IP клиента (после разбора заголовков прокси). Увеличьте, если много устройств выходят в сеть с одного публичного IP. |
| `SOFTWARE_UPDATE_CHECK` | `N` | `Y` возвращает ежедневную проверку версии из upstream: POST-запрос на `https://api.rustdesk.com/version/latest` с отпечатком хоста. Не зависит от `WS_REGISTER`. См. [«Исходящие соединения»](#исходящие-соединения). |

Другие важные здесь настройки:

* `-r <domain>` (`RELAY_SERVERS`): ретранслятор, который сообщается
  устройствам и управляющим устройствам. Укажите публичное имя, например
  `-r patina.example.com`. При запуске `hbbs` отбрасывает имена, которые не может
  разрешить, поэтому имя должно разрешаться внутри контейнера. Это также
  список разрешённых ретрансляторов для `RequestRelay` к WS-устройствам.
* Ключ: оставьте проверку ключа включённой (`-k _` у `hbbr`; `hbbs` проверяет
  свой ключ по умолчанию).
* WebSocket-порт `hbbs` — `port + 2` (21118), у `hbbr` — 21119. **Не
  публикуйте их**: к ним должен иметь доступ только прокси.

Ограничения соединений действуют и при `WS_REGISTER=N`: тайм-аут рукопожатия
10 с, лимит сообщения 64 КиБ и `MAX_WS_CONN_PER_IP`. Это же относится к
правилу для заголовков прокси. Конфигурации upstream, которая полагалась на
то, что `hbbs` доверяет `X-Real-IP` от любого узла, после перехода на Patina
нужна `TRUSTED_PROXY_CIDRS`.

Если `TRUSTED_PROXY_CIDRS` не включает прокси, `hbbs` пишет в журнал `Ignoring
X-Real-IP/X-Forwarded-For from untrusted peer ...`, и все WebSocket-клиенты
выглядят так, будто приходят с адреса прокси. Тогда все устройства делят
лимиты одного IP:

* `MAX_WS_CONN_PER_IP` (64 соединения);
* блокировку по IP из upstream, которая отвечает `TOO_FREQUENT`, как только с
  одного адреса регистрируются слишком часто или слишком много разных id;
* учёт `IP_CHANGES`.

Исправьте настройку, а не увеличивайте лимиты.

## Обратный прокси

Конфигурация прокси —
[`deploy/swag/patina.subdomain.conf`](../deploy/swag/patina.subdomain.conf),
proxy-conf linuxserver/SWAG для отдельного поддомена. Используйте её как
фрагмент конфигурации nginx и в других установках. `hbbs` зависит от
следующих её частей:

* `location = /ws/id` ведёт на `hbbs:21118`, а `location = /ws/relay` — на
  `hbbr:21119`, с заголовками Upgrade.
* `X-Real-IP $remote_addr`, `X-Real-Port $remote_port` и
  `X-Forwarded-For $remote_addr` **перезаписывают** то, что прислал клиент.
  Никогда не дописывайте значение клиента. Если прокси только дописывает
  `X-Forwarded-For` и не трогает `X-Real-IP`, клиент может добавить
  `X-Real-IP`, который не совпадает с последним узлом цепочки. Тогда `hbbs`
  использует адрес прокси (см. [«Адреса за прокси»](#адреса-за-прокси)).
* `proxy_read_timeout 240`. Это намного больше интервала keepalive в 12 с,
  поэтому тайм-аут срабатывает, только если узел не отвечает. Значение nginx
  по умолчанию, 60 с, тоже подойдёт, но оставляет мало запаса.
* `location /api/` отвечает `{}`. `api-server=https://...` нужен клиенту
  только для выбора `wss://`. Никакого API за ним нет.
* На всё остальное — 404.

Прокси должен иметь доступ к `hbbs` и `hbbr` в их сети Docker. SWAG для этого
подключите к этой сети. В `TRUSTED_PROXY_CIDRS` у `hbbs` укажите подсеть этой
сети. Вся схема целиком показана в
[`deploy/docker-compose.example.yml`](../deploy/docker-compose.example.yml).

## Настройки клиента (WebSocket-устройства)

В [`deploy/client-settings.ru.md`](../deploy/client-settings.ru.md) есть все
настройки, настройка из командной строки, рекомендуемая защита и раздел о
решении проблем. Кратко:

* «Сервер ID» = «Ретранслятор» = `<domain>`, никогда не IP-адрес. С IP-адресом
  получается незашифрованный `ws://IP:21118`, в обход прокси и TLS.
* В поле «Сервер API» укажите `https://<domain>`. Клиент использует `wss://`,
  только если адрес сервера API начинается с `https`.
* `Key` = открытый ключ сервера (`id_ed25519.pub`).
* «Использовать WebSocket» = включено (`allow-websocket=Y`).
* Оставьте `allow-insecure-tls-fallback` выключенным. В режиме WebSocket
  клиент не выполняет обмен ключами с сервером ID и защищает этот участок
  только с помощью TLS.
* Это компьютеры третьих лиц, поэтому включите также 2FA, подтверждение
  нажатием (`approve-mode=click`) и белый список ID (`id-whitelist`, появился
  в 1.5.0).

Белый список IP на устройстве проверяет адрес управляющего устройства,
который `hbbs` поместил в `PunchHole` (для управляющего устройства в режиме
WebSocket — адрес, полученный из заголовков прокси). Адрес `hbbr` он не
проверяет. Поэтому он надёжен ровно настолько, насколько правильно задан
`TRUSTED_PROXY_CIDRS`.

Управляющие устройства могут работать в любом режиме. Управляющее устройство
в режиме WebSocket работает через тот же прокси. Обычное управляющее
устройство в режиме UDP/TCP работает через опубликованные порты 21115-21117.

## Модель угроз

Что защищается: какое соединение получает трафик для id устройства (а вместе с
этим и возможность получать попытки подключения к этому устройству);
IP-адреса устройств; доступность сервера ID. Сами удалённые сеансы зашифрованы
сквозным шифрованием между узлами, а управляющее устройство проверяет ключ
устройства, подписанный ключом сервера. Скомпрометированный путь через сервер
ID может вызвать отказ в обслуживании, но не может прочитать сеансы.

| Угроза | Защита |
| --- | --- |
| Захватить зарегистрированный id через WebSocket | Те же правила владения uuid/pk, что и для UDP: другой uuid получает `UUID_MISMATCH`, а маршрут остаётся у владельца; uuid никогда не передаётся управляющим устройствам. Регистрация через WS ровно так же надёжна, как регистрация через UDP в upstream, и не надёжнее: первая регистрация неизвестного id выполняется по принципу «кто первый, того и id», как в upstream. |
| Привязать id через `RegisterPeer` | Невозможно: `RegisterPeer` — только обновление для id, который то же соединение уже зарегистрировало через `RegisterPk`. |
| Удерживать чужой id «в сети» | Heartbeat учитывается только от соединения, которому принадлежит id. |
| Отключить устройство, переподключившись | Чтобы заменить маршрут, нужен `RegisterPk`, который проходит проверки uuid/pk, как описано выше. |
| Подделать IP клиента (чтобы обойти блокировку по IP или засорить журналы) | Заголовки прокси только от `TRUSTED_PROXY_CIDRS`; повторяющиеся, неразбираемые или противоречащие друг другу заголовки заменяются адресом прокси (fail closed). 21118/21119 нельзя публиковать. |
| Узнать IP WS-устройства | WS-устройства всегда работают через ретранслятор, поэтому управляющие устройства видят только `hbbr`. `RequestRelay` к WS-устройству должен называть ретранслятор из `-r`. На `FetchLocalAddr` тоже отвечают через ретранслятор. |
| Исчерпать память или соединения | Ограниченный канал для каждого соединения; `MAX_WS_PEERS`; `MAX_WS_CONN_PER_IP`; тайм-аут рукопожатия 10 с; лимит сообщения 64 КиБ; тайм-аут чтения 30 с для молчащих соединений; блокировка по IP и ограничение частоты `reg_pk` из upstream для `RegisterPk`. Ни одна блокировка таблицы не удерживается через `.await`. |
| Опознать или отследить хост сервера извне | `hbbs` не обращается к третьим сторонам по своей инициативе. Проверка версии из upstream, которая при запуске и затем ежедневно отправляет на `api.rustdesk.com` отпечаток хоста, выполняется только при `SOFTWARE_UPDATE_CHECK=Y`. См. [«Исходящие соединения»](#исходящие-соединения). |
| Перехватить участок до сервера ID | TLS до прокси (в режиме WS клиент не выполняет KeyExchange). Участок от прокси до `hbbs` — обычный HTTP в сети Docker. Посредник (MITM) без ключа сервера не может подделать подписанный ключ устройства, но может видеть метаданные и вызвать отказ в обслуживании. |

Принятые риски:

* `RegisterPk` не требует ключа сервера ни по UDP, ни по WS, как в upstream.
  Новый id может зарегистрировать кто угодно; ключ защищает запросы на
  подключение (`PunchHoleRequest`).
* `RequestRelay` не содержит лицензионного ключа, как в upstream, поэтому его
  нельзя аутентифицировать. Для WS-устройств он ограничен ретрансляторами из
  `-r`; для UDP-устройств поведение как в upstream.
* Loopback всегда считается доверенным прокси, поэтому процесс внутри
  контейнера `hbbs` может задавать эти заголовки.
* `hbbr` не изменён и по-прежнему доверяет `X-Real-IP` от любого, кто может
  подключиться к 21119. Не публикуйте 21119.
* `hbbs` записывает в журнал id устройств и IP клиентов, как в upstream.
* Тот, кто отправляет `RelayResponse` или `PunchHoleSent` по TCP/WebSocket,
  выбирает управляющее устройство, которому они уйдут, по адресу, как в
  upstream. Patina делает эти адреса уникальными для каждого соединения
  (`X-Real-Port` или идентификатор соединения вместо `IP:0`). Это не даёт двум
  управляющим устройствам за одним NAT получать ответы друг друга. Но адреса
  по-прежнему не секретны. Подделанный ответ может направить ожидающее
  управляющее устройство на другой ретранслятор. Выдать себя за устройство он
  не может, потому что управляющее устройство проверяет ключ устройства,
  подписанный ключом сервера.

## Ограничения

* **Только через ретранслятор** для WS-устройств: нет hole punching, нет
  прямых и локальных (LAN) подключений. Клиент в режиме WS и так
  принудительно использует ретранслятор.
* **Нет WebRTC/ICE**: `hbbs` не передаёт offer, answer и кандидатов (открытый
  сервер upstream тоже этого не делает).
* **Клиенты на обычном TCP с отключённым UDP (не WS) по-прежнему не
  поддерживаются**: им нужен `KeyExchange` на сервере ID, которого в открытом
  `hbbs` нет.
* Состояние регистрации хранится в памяти одного процесса `hbbs`. После
  перезапуска устройства переподключаются и регистрируются снова (тот же id,
  тот же ключ; см. отчёт о тестировании).
* Нет функций Pro: сервер API, адресная книга, группы устройств и т. п. не
  предоставляются.

## Авторство и лицензия

Patina распространяется по лицензии GNU AGPL v3, как и upstream (см.
[LICENSE](../LICENSE)). Уведомления об авторских правах upstream сохранены.
У новых файлов свои заголовки.

Идеи устройства взяты из двух других форков под AGPL-3.0. Код из них не
копировался:

* [ymg2006/rustdesk-server](https://github.com/ymg2006/rustdesk-server):
  маршруты WebSocket с ключом из id узла и идентификатора соединения
  (побеждает новейшее, очистка с проверкой владельца), маршрутизация
  `PunchHole` / `FetchLocalAddr` / `RequestRelay` в WebSocket и
  `TRUSTED_PROXY_CIDRS`.
* [bropines/rustdesk-server](https://github.com/bropines/rustdesk-server),
  ветка `rdpanel`: пустой бинарный keepalive-кадр, на который клиент отвечает
  эхом, что обновляет `last_reg_time`.

В [PATCHES.ru.md](../PATCHES.ru.md#указание-авторства) перечислено, что из
них сознательно не взято.
